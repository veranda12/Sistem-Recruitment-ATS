# Bangun sistem rekrutmen enterprise

Anda bekerja sebagai engineer penanggung jawab implementasi di Claude Code, Opus 5.5 effort Medium, pada direktori proyek lokal Windows. Baca instruksi ini sampai akhir, periksa repository, lalu implementasikan produk melalui alur pengguna yang nyata. Tulis antarmuka dan panduan operator dalam bahasa Indonesia. Gunakan nama teknis yang konsisten di kode. Setiap fase berakhir dengan build atau pengujian yang bisa diulang. Lanjutkan ke fase berikutnya selama lingkungan memungkinkan.

## Hasil yang harus dapat didemonstrasikan

HR menerbitkan lowongan dengan workflow yang sudah disetujui. Satu kandidat membuat profil sekali, melamar dua lowongan, lalu mengikuti ujian lewat ponsel. Saat koneksi putus, kandidat bisa membedakan jawaban yang masih ada di perangkat dari yang sudah diterima server. Setelah tersambung kembali, kandidat menyelesaikan ujian dan memperoleh bukti penerimaan. Nilai yang sudah dirilis memicu percabangan workflow pada lamaran terkait. Hiring manager menyetujui keputusan, recruiter mengirim pemberitahuan, dan HR dapat menelusuri alasan serta pelaku setiap perubahan. Demonstrasikan juga jalur nilai di bawah ambang, permintaan penilaian manual, penolakan, dan penarikan lamaran.

Bangun produk yang dapat dibeli putus, dipasang di infrastruktur pelanggan, serta diteruskan tim pelanggan tanpa akun cloud pengembang. Gunakan organisasi fiktif yang konsisten dalam seed. Pengalaman pengembang dengan Agung Sedayu Group adalah konteks portofolio, bukan izin memakai merek, source code, soal, atau data pelamar mereka.

**Asumsi awal yang perlu ditandai di dokumentasi produk.** Satu organisasi per instalasi dengan beberapa unit dan lokasi. UI berbahasa Indonesia, tanggal ditampilkan menurut zona organisasi (awal Asia/Jakarta), penyimpanan waktu absolut menggunakan timestamptz. Satu akun kandidat per identitas terverifikasi secara internal. Verifikasi email membuktikan akses email saja. Integrasi Dukcapil, SSO perusahaan, WhatsApp, proctoring video, dan keputusan hiring otomatis tidak termasuk asumsi dasar. Catat kebijakan retensi, kesempatan retake, akomodasi waktu, pemberitahuan nilai, SLA dukungan, RPO dan RTO sebagai keputusan yang harus dikonfirmasi. Buat pengaturan yang diperlukan tanpa menjanjikan integrasi atau kontrak yang belum tersedia.

## Keputusan arsitektur

Gunakan modular monolith Go + Gin, dengan proses API dan worker yang dapat diskalakan terpisah dari satu repo. React 19 + Vite + TypeScript strict memberi satu frontend untuk career portal, ruang kandidat, ujian, dan back office. Pisahkan bundle per area. Gunakan Tailwind dengan primitive Radix atau shadcn yang dikustomisasi. PostgreSQL 17 menjadi sumber kebenaran. Gunakan pgxpool + sqlc agar SQL, transaksi dan rencana eksekusi dapat diperiksa. Kelola skema memakai golang-migrate. Pilih Redis untuk rate limiting lintas instance, cache data publik dan antrean Asynq. Simpan berkas di bucket privat MinIO/S3-compatible. Nginx melayani aset frontend dan meneruskan API melalui origin yang sama. Gunakan Go test, Vitest, Playwright, k6, structured logging, Prometheus, Grafana dan tracing OpenTelemetry yang bisa dikonfigurasi.

API stateless terhadap instance. Simpan sesi autentikasi yang dapat dicabut di PostgreSQL. Gunakan transactional outbox untuk menghubungkan transaksi bisnis dengan pekerjaan asinkron. Worker memiliki retry berbatas, backoff dengan jitter, deduplikasi berdasarkan event ID, dead-letter serta prosedur replay dengan audit. Anggap delivery minimal satu kali. Untuk email, gunakan idempotency provider bila tersedia, dan tandai pengiriman ambigu untuk rekonsiliasi. Hindari mengirim email di dalam transaksi database. Kegagalan email atau Redis tidak boleh membatalkan jawaban yang telah diakui server.

Cache daftar lowongan publik dengan TTL pendek dan invalidasi setelah publish/close. Tetap periksa status lowongan langsung di transaksi apply. Hindari cache bersama untuk identitas, hak akses yang dapat dicabut, deadline, jawaban, hasil belum dirilis, atau state workflow. Saat Redis mati, matikan cache, batasi traffic lewat Nginx dan limiter lokal konservatif, tunda dispatch outbox, serta tampilkan kondisi degraded. Tetapkan kapan endpoint sensitif harus menolak permintaan jika perlindungan tidak tersedia. Pisahkan readiness API ujian dari readiness worker dan dependensi opsional.

Struktur awal yang disarankan, sesuaikan jika sudah ada konvensi repo:

    backend/cmd/{api,worker,seed}
    backend/internal/{auth,identity,recruitment,workflow,exam,documents,notify,reporting,settings,platform}
    backend/db/{migrations,queries,sqlc}
    frontend/src/{app,features,ui,lib}
    contracts/openapi.yaml
    tests/{e2e,load,fixtures}
    ops/{windows,nginx,systemd,monitoring,backup}
    docs/{architecture,product,operations,handover}

Setiap modul memiliki service untuk aturan bisnis, query bernama dan handler tipis. Caller memasok transaksi ke query yang harus commit bersama. Jaga dependensi satu arah. Pisahkan DTO kandidat dari model penilaian internal. Tetapkan batas request body, deadline per kelas operasi, propagasi context, cancellation, graceful drain API dan worker. Anggarkan total koneksi semua replica + worker + migrasi di bawah max_connections dengan cadangan administrasi. Dokumentasikan contoh perhitungan dan ukur pool wait, slow queries, lock waits serta panjang antrean sebelum menaikkan pool.

## Data dan API

Buat ERD dan kamus kolom. Kelompok inti mencakup organizations, units, locations, users, sessions, roles, permissions, role_permissions, scoped_role_assignments, candidate_profiles, candidate_identities, education, experiences, certifications, documents, requisitions, job_openings, job_applications, application_snapshots, assignments, interviews, evaluations, hiring_decisions, workflows, workflow_versions, stages, rules, approvals, transition_history, question_banks, question_versions, exam_package_versions, exam_schedules, exam_participants, exam_attempts, attempt_items, exam_answers, exam_submissions, exam_results, notifications, templates, delivery_attempts, outbox, exports, audit_logs, system_settings. Gunakan FK termasuk scope organisasi pada relasi yang memerlukannya. Pilih kolom typed untuk data yang difilter dan constraint relasional. Gunakan JSONB untuk definition/snapshot berversi yang divalidasi. Simpan applied_at dan stage_entered_at terpisah, serta histori append-only untuk metrik.

Satu NIK diperlakukan sebagai string 16 digit, pertahankan nol di depan. Normalisasi deterministik dengan validasi digit ASCII. Simpan ciphertext AEAD dengan nonce unik dan key version, serta blind index HMAC berkunci terpisah untuk equality lookup. Terapkan unique constraint atas organisasi dan blind index, termasuk saat registrasi simultan. Dokumentasikan rotasi kunci pencocokan dengan dual-write, backfill tervalidasi, penjagaan uniqueness sepanjang migrasi, dan cutover. Jangan pakai hash polos atau NIK sebagai credential. Tampilkan identitas tersamar, reveal perlu permission, alasan dan audit. Bila NIK sudah terkait akun lain, berikan respons publik netral dan jalur verifikasi manual. Jangan merge otomatis lewat nama, telepon atau kecocokan NIK saja.

Gunakan unique(job_id,candidate_id) untuk asumsi satu lamaran per publikasi. Sepakati aturan bila posisi dibuka ulang. Buat indeks komposit sesuai akses seperti (job_id,stage_id,applied_at,id), (candidate_id,applied_at,id), (schedule_id,status), unique(attempt_id,item_id), dan indeks parsial outbox pending. Jalankan EXPLAIN ANALYZE pada dataset sintetis representatif di staging. Terapkan keyset pagination untuk histori besar dengan tie-breaker ID. Hindari COUNT seluruh dataset pada setiap reload. Gunakan FK restrict untuk histori penting, kebijakan penghapusan eksplisit, serta migrasi dan backfill bertahap untuk tabel besar.

Spesifikasi OpenAPI harus mendeskripsikan request, response kandidat/staf, filter allowlist, batas page size, cookie, CSRF, error dan contoh. Kembalikan error code mesin stabil, pesan UI Indonesia, fieldErrors dan requestId. Bedakan validasi, unauthenticated, forbidden, not found, conflict, payload terlalu besar, rate limit dan unavailable. Untuk operasi penting, scope Idempotency-Key per aktor + operasi + resource, simpan digest payload dan hasil dalam transaksi yang sama. Pengulangan identik mengembalikan hasil lama, payload berbeda menghasilkan konflik. Optimistic concurrency untuk edit administratif. Periksa kontrak tipe frontend terhadap OpenAPI di build.

## Mesin workflow yang benar-benar berjalan

Definisikan graph berarah per versi, satu titik awal, terminal eksplisit, stage bertipe screening/interview/assessment/approval/decision, edge berurutan dengan default. Buat rule DSL deklaratif dengan field, operator dan tipe allowlist, misalnya assessment.score >= 75 AND assessment.status = released. Tentukan perlakuan null sebagai belum memenuhi syarat. Batasi kedalaman, jumlah node serta evaluasi per event. Larang eval, SQL bebas, callback URL dan scripting. Tolak siklus, target hilang, cabang tanpa fallback, node tak terjangkau, terminal dengan outgoing edge, dan permission approval kosong. Guard persetujuan menyertakan peran, scope, quorum dan kebijakan self-approval.

Draft bisa diubah. Publish menghasilkan versi immutable. Saat apply, pin versi aktif dan stage awal dalam satu transaksi. Engine menerima command/event dengan execution ID unik, lock lamaran, periksa state asal + versi, evaluasi guard, tulis approval/transisi/history/outbox secara atomik. Rekam aktor, alasan, rule/version, ringkasan input tersamar dan keputusan. Simulasi memakai evaluator yang sama tanpa side effect. Rollback memilih versi published sebelumnya bagi lamaran baru. Migrasi lamaran berjalan memerlukan mapping stage, dry-run, audit dan persetujuan operator. Uji dua approver serentak, duplicate event, guard gagal, branch default, stale approval setelah withdrawal dan publish bersamaan. Sertakan workflow seed Screening → Ujian → Interview → Persetujuan → Diterima dengan cabang review/ditolak. Hasil ujian memicu transisi hanya pada lamaran dan versi assessment yang sesuai.

## Protokol ujian dan jaminan atas jawaban

- Saat mulai, POST /exam-invitations/{id}/start mengunci assignment dan memeriksa peserta, jadwal, kuota attempt dan eligibility. Tetapkan started_at dan deadline_at di server termasuk extra time dan batas sesi. Simpan versi paket, seed privat, versi algoritma serta urutan item/opsi final per attempt. Perubahan bank soal tidak mengubah ujian berjalan. Retry start mengembalikan attempt yang sama.
- Endpoint resume mengembalikan state, server_time, deadline_at, urutan soal dan revisi jawaban yang sudah commit. Gunakan ID opsi opaque. DTO ujian sama sekali tidak memuat correct flag, pembahasan, bobot yang membocorkan kunci, atau seed privat. Pisahkan endpoint examiner. Gunakan Cache-Control private, no-store. Navigasi lokal dalam halaman soal yang sudah dimuat tidak memicu write bila jawaban tetap sama.
- Client menyimpan dirty answers, melakukan debounce awal 800 ms dengan batas tunda 3 detik saat terus mengetik, flush saat pindah soal serta sebelum submit. Batch hanya item yang berubah. Tiap mutasi membawa operation ID stabil dan base revision tiap jawaban. Serialisasi flush per attempt, gabungkan edit baru saat request masih berjalan. Tampilkan “Menyimpan”, “Tersimpan pukul …”, “Menunggu koneksi” dan konflik. Label tersimpan hanya muncul setelah ACK commit server.
- PUT /exam-attempts/{id}/answers menerima batch terbatas. Dalam transaksi pendek, lock attempt, validasi peserta, status, deadline dengan jam DB aktual setelah memperoleh lock, keanggotaan item, nilai dan revisi. Apply batch atomik, simpan receipt digest + revisi baru. Kirim ACK setelah commit. Retry setelah ACK hilang harus dapat mengambil receipt terdahulu meskipun deadline sudah lewat. Revisi basi menghasilkan konflik dengan state server yang dibutuhkan untuk resolusi eksplisit. Redis tidak berada di jalur durability. Uji race dua tab dan permintaan terlambat.
- Gunakan draft lokal minimal terikat user dan attempt di IndexedDB untuk pemulihan refresh pada perangkat yang sama. Batasi TTL, hapus pada logout, finalisasi dan pergantian akun. Jelaskan konsekuensi pada perangkat bersama. Draft offline belum dijamin diterima server. Saat reconnect lakukan resume, bandingkan revisi, kirim ulang operation ID yang sama, tampilkan konflik tanpa overwrite diam-diam. Countdown client dikalibrasi ulang dengan server_time. Jam klien dan klaim waktu offline tidak memperpanjang deadline.
- POST /exam-attempts/{id}/submit membawa idempotency key dan revisi yang diharapkan. Izinkan membawa batch jawaban terakhir agar pemeriksaan, persist, pembekuan snapshot dan pembuatan satu receipt berada dalam satu transaksi. Gunakan urutan locking yang sama dengan autosave dan expiry. Uji autosave yang tiba sebelum dan sesudah submit. Setelah final, retry submit identik mengembalikan receipt yang sama, write baru ditolak. Worker expiry mengunci attempt dan memfinalisasi jawaban terakhir yang committed. Asumsi awal batas waktu ketat, tanpa grace period. Saat jaringan putus sampai lewat deadline, jelaskan hasil final dan arahkan ke proses keberatan yang diaudit.
- Skoring objektif dihitung dari snapshot dan versi kunci privat; asumsi pilihan jamak harus cocok seluruh himpunan. Esai menunggu penilaian manual. Simpan versi rubric, assessor, riwayat koreksi dan alasan regrade. Regrade tidak menggandakan transisi ATS. Rilis skor merupakan aksi terpisah. Monitoring staf membedakan last_seen, progres jawaban committed dan submitted. Heartbeat dengan jitter sekitar 30 detik bersifat best-effort, tidak memperpanjang sesi. Gunakan polling agregat berindeks untuk dashboard, hindari satu query per peserta.
- Prioritaskan start/save/submit dibanding ekspor, heartbeat dan analytics. Batasi concurrency per operasi, ukuran batch, queue dan waktu tunggu. Berikan Retry-After dan jitter untuk overload yang dapat dipulihkan. Jangan mengakui write sebelum durable atau memasukkan peserta ke antrean tanpa batas. Pisahkan pool worker berat agar ekspor tidak menghabiskan koneksi API.

## Pembuktian performa

Bangun skenario k6 dengan 500 kandidat sintetis unik, cookie jar terpisah, satu undangan valid per VU dan data setup terpisah dari pengukuran. Uji pada staging yang disetujui, bukan layanan eksternal atau produksi. Pisahkan smoke 5 VU, baseline 100, kenaikan ke 500, plateau sedikitnya 20 menit, dan burst tersinkron. Untuk plateau pastikan 500 attempt aktif tumpang tindih, cukupkan durasi jadwal, jangan mengganti peserta yang selesai dengan login berulang. Ukur dengan metrik server dan VU aktif. Setiap VU login, start, load soal, memilih jawaban, mengetik/mengubah, navigasi, autosave, heartbeat, resume sesuai probabilitas, dan submit. Gunakan seed serta think time yang dapat diulang. Pisahkan profil login/start 500 dalam 30 detik dan 500 final submit dalam 10 detik.

| Target awal pada lingkungan uji yang dicatat | Cara menilai |
|---|---|
| 500 peserta aktif; rata-rata satu batch save per peserta per 10 detik dan heartbeat per 30 detik | Harapkan sekitar 50 batch save/detik dan 17 heartbeat/detik, di luar baca. Laporkan offered, completed, retry, rejected dan dropped iterations. Burst submit menawarkan 50 submit/detik. Pastikan generator sendiri tidak jenuh. |
| p95 save ≤400 ms, p99 ≤1 s; p95 load/resume ≤800 ms, p95 submit ≤1 s, p99 submit ≤2 s; p95 login/start masing-masing ≤1,5 s | Ukur end-to-end per route dan fase menggunakan tag berkardinalitas rendah. Laporkan cold/warm run dan latency burst tersendiri. |
| Unexpected error <0,5% per operasi; nol finalisasi ganda, ACK palsu, lintas peserta, atau ACK yang hilang dari histori persist | Pisahkan planned failures dari error normal; 429 dan timeout pada beban nominal dihitung sebagai kegagalan. Retry sukses tidak menghapus kegagalan awal. |
| CPU rata-rata API/DB <75% saat plateau, memori <80% anggaran, tanpa pertumbuhan berkelanjutan; p95 pool wait <50 ms | Catat spesifikasi generator/API/DB, replika, disk, batas memori, koneksi, utilisasi worker, Redis, disk latency, lock waits dan query dominan. Laporkan puncak burst terpisah. |

Bangun oracle independen dari response aplikasi. Hasilkan ledger per peserta berisi operation ID, jawaban yang dikirim, ACK/revisi dan hasil akhir yang diharapkan. Rekonsiliasi dengan query read-only pascauji pada snapshot final, receipt, revisi yang diterima serta jumlah hasil. Bandingkan nilai aktual dengan kunci fixture secara independen. Jawaban yang sengaja diubah harus cocok dengan revisi terakhir yang diterima. Simulasikan respons hilang setelah commit, offline sebelum ACK, dua tab, API restart, Redis mati saat save, worker berhenti lalu pulih, serta expiry bersamaan dengan submit. Untuk tiap gangguan catat state yang diharapkan, durasi pemulihan dan selisih data.

Simpan konfigurasi, perintah, commit, timestamp, dataset, threshold dan ringkasan hasil. Jalankan ulang setelah optimasi dan tunjukkan bottleneck yang berubah. Bila laptop hanya cukup untuk smoke, laporkan hasil smoke dan sertakan skrip lengkap serta runbook staging. Klaim kapasitas hanya untuk konfigurasi yang benar-benar lulus seluruh acceptance gate terkait.

## Keamanan, privasi dan operasional

Buat threat model defensif yang memetakan trust boundary kandidat/staf, API, worker, file dan data store. Pilih versi OWASP ASVS dan OWASP Top 10 yang digunakan, catat sumber resmi, kontrol relevan, implementasi, pengujian, bukti dan residual risk. Gunakan password hashing Argon2id dengan parameter yang diukur terhadap anggaran memori saat burst login. Gunakan token sesi acak berentropi tinggi, simpan digest, cookie HttpOnly/Secure/SameSite, idle dan absolute expiry, rotasi saat login/elevasi, revoke saat reset/logout. Lindungi mutasi cookie dengan token CSRF dan pemeriksaan origin, same-origin default, allowlist CORS terbatas. Reset dan verifikasi memakai token singkat sekali pakai yang disimpan sebagai digest, respons netral dan throttling. Sediakan MFA untuk staf berprivilege dan recovery code sekali pakai. Tidak boleh ada sandi default produksi.

Validasi input dan parameter SQL, petakan sort ke allowlist, escape output, batasi rich text, tetapkan CSP dan header yang sesuai, TLS, trusted proxy eksplisit. Upload CV ke karantina privat, batasi ukuran, cek signature file dan tipe yang diizinkan, nama objek acak, pindai malware sebelum tersedia. Jika scanner tidak tersedia, status tetap pending. Verifikasi pemilik dan scope sebelum menerbitkan URL unduh berumur pendek. Gunakan kredensial per layanan, enkripsi volume/backup dan pemisahan kunci dari backup. Tidak boleh merekam NIK, isi jawaban, CV, cookie, password, reset token atau URL bertanda tangan pada log/trace.

Buat daftar tujuan pemrosesan, aliran data, dasar pemrosesan untuk dikonfirmasi pemilik kebijakan, versi pemberitahuan privasi, alur permintaan akses/koreksi/penghapusan, verifikasi pemohon, retensi per kategori, legal hold dan bukti eksekusi. Perhitungkan salinan ekspor, object storage dan pemulihan backup agar data yang sudah dihapus tidak muncul lagi tanpa penanganan. Audit memuat actor, action, target, waktu, scope, outcome dan request ID; batasi akses mutasi dan ekspor audit. Jelaskan hal yang membutuhkan keputusan legal/HR untuk penerapan UU PDP. Jangan mengklaim sertifikasi, kepatuhan hukum, lulus VAPT atau SLA vendor.

Sediakan inventory dependensi dan lisensi untuk buyout, scanning Go/npm, secret scanning, triage severity, penanggung jawab, target perbaikan yang diusulkan serta retest. Paket kesiapan VAPT berisi arsitektur, scope staging, akun uji per role, checklist kontrol, template bukti dan register temuan hingga closure. Hasil audit independen hanya dicatat bila benar-benar tersedia.

## Definition of Done dan laporan terakhir

Tandai setiap butir sebagai lulus, gagal, atau belum diuji, sertakan path bukti dan perintah reproduksi.

- Checkout bersih dapat dijalankan di Windows tanpa Docker. Build Linux dan instruksi produksi cocok dengan layout repository.
- Semua aksi yang ditampilkan di UI terhubung ke backend, bertahan setelah refresh, memvalidasi input, memberikan status yang jelas dan memeriksa otorisasi.
- Single NIK, beberapa lamaran, histori, snapshot dan recovery akun teruji. Tidak ada PII mentah di log atau fixture nyata.
- Workflow yang dibuat admin dapat dipublikasikan, disimulasikan dan dijalankan. Histori menjelaskan mengapa keputusan terjadi.
- Satu attempt menghasilkan maksimal satu submission. Tidak ada jawaban berstatus tersimpan yang hilang akibat retry atau race. Nilai dan receipt dapat direkonsiliasi.
- Ada hasil pengujian realistis untuk skala yang benar-benar dijalankan, termasuk burst submit dan integritas. Klaim target 500 harus mencantumkan hasil staging dan hardware.
- Seluruh role, dashboard, laporan, notif, upload, tampilan mobile, akses keyboard, kontrol keamanan, deployment dan restore punya bukti atau catatan keterbatasan spesifik.
- Pengelola baru dapat memakai dokumentasi untuk menjalankan, memperbarui, memulihkan dan memelihara aplikasi. Handover menyebut pemilik keputusan yang masih terbuka.

Jika batas konteks mendekat, simpan docs/STATUS.md berisi fase, file utama, migrasi terakhir, uji beserta hasil aktual, blocker dan satu langkah konkret berikutnya. Saat lanjut, baca status, periksa Git dan verifikasi kondisi sekarang. Jangan berhenti pada scaffold, mengganti endpoint final dengan mock, menghapus tes yang gagal, atau menandai pekerjaan selesai hanya karena kodenya sudah ditulis. Pada akhir pekerjaan laporkan alur yang bisa dicoba, cara menjalankan, hasil uji aktual, risiko tersisa dan hal yang memerlukan keputusan pelanggan.
